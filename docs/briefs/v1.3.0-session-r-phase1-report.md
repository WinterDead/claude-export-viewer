## The scanner

`tools/scan_export_schema.py` — stdlib-only, aggregate-only schema profiler, committed for
any user of the public repo and for future format shifts. Input: a legacy single-zip export,
a manifest `.json`, or a directory holding a new-format set (any subset of category zips;
non-category zips in a directory are treated as standalone legacy archives). Multi-part
category files are grouped and merged per category — structural tolerance only, stated in
the docstring, since only part `000` has ever been observed. Output per JSON document: every
path with observed types and counts, dict optional-key presence ratios, string/list
min/max/avg lengths, empty and frontmatter-fence counts, capped distinct counts,
UUID/timestamp shape counts, boolean value counts, and value censuses for the brief's
allowlisted machine-enum fields.

Privacy is by construction, not operator discipline: the enum allowlist and machine-enum
shape check (short single token, no whitespace, no sentence punctuation; failures print as
`<masked len=N>`), UUID masking of values **and dictionary keys** (the `project_memories`
lesson), masked non-identifier dict keys and zip member names, and a
`memory_files[].path`-only top-level-segment census (slugs below the top level never print).
Run against the synthetic legacy fixture first, then `data/export-2026-08/`; no
non-allowlisted real value appeared in any output (the scanner-output hard stop was never
approached).

Per local convention the tool has no pytest file (`tools/scan_artifacts.py` has none); its
verification is the fixture run plus the real-export reproduction below.

## Format facts beyond the chat-side table

Recorded for the schema doc (all now in `docs/export-schema.md`) and the design record:

1. **Leading `/` on `memory_files` paths** (row 5 addition above).
2. **Manifest extras**: `version` (3-char string — the export's first versioned surface),
   `created_at`, `instructions`, `total_files`; `batch_index` enumerates files rather than
   staying 0.
3. **New block-level keys** not in the chat-side list: `approval_key_legacy` (null
   throughout), `hidden` (bool, thinking), `hidden_in_chat` (null, tool blocks),
   `thinking_hidden` (bool — **true on 174 of 3,585** thinking blocks),
   `tool_identifier` (null), `initial_turn_only` / `prompt` /
   `skip_on_truncated_continuation` (the injected_prompt_block trio),
   `citations_grouping_mode` (4 text blocks, value `combine`).
4. **`meta.output_format_category`** on 634 tool_results: `md:363, none:216, other:50,
   svg:2, react:2, html:1`.
5. **Knowledge inner blocks gain `links`** (list on 65, null on 14,154);
   `prompt_context_metadata` gains `age`, `content_type` (`html`), `destination_url`,
   `final_url`, `mime_type`; `search_provider` census `anthropic:14035` (legacy-era values
   differed).
6. **`structured_content` can be a dict** (15 blocks): file-tool target descriptions
   (`parsed`/`path`/`target`/`version`), singly or as a `documents` list.
7. **`summaries` items are dicts** — `{summary: str}`, 9,322 items total.
8. **Timestamp unification in conversations.json**: conversation, message, and block
   timestamps all 27 characters (Z-suffixed microsecond form) — legacy messages used the
   32-character offset form. Category files (manifest, projects, memories, login history)
   use the 32-character offset form. Length-derived inference; the profiler prints no
   values.
9. **No `image` inner type** appears in the current reference's tool_results (legacy had
   it) — archive absence, not schema removal.
10. **`is_error` true on 122** of 3,227 tool_results; `tool_origin` sparse
    (`first_party:204`); `is_mcp_app` boolean on 19 blocks (true:12, false:7).
11. **`users.json` unchanged** in shape; `verified_phone_number` populated (12 chars).
12. The internal-layout inconsistency the brief flags is confirmed: projects and memories
    keep subdirectories inside their zips; conversations and light_metadata are root-level.

## Open design questions (for the chat design record — not answered here)

Carried verbatim from the brief:

- Multi-part assembly.
- Subset-upload behaviour and the degraded-view banner.
- Whether the manifest plays any role in upload.
- Upload-history fingerprint semantics across four files.
- New-memory rendering (file tree? frontmatter presentation?).
- FTS scope over `memory_files` and `conversations_memory`.
- Login-history presentation (ratified *that* it displays; *how* is open).
- Render policy for `injected_prompt_block`, `display_content`, `summaries`, and
  `signature`.
- Inspect-mode behaviour across both formats.
- Detection/sniffing rules.

Added by this session's scan:

- Whether `thinking_hidden` (true on 174 blocks) should suppress or badge those thinking
  blocks in the viewer, and whether the export serializer should honour it.
- Render policy for text-block `citations` (597 web-search citations with offsets) — the
  legacy renderer never had non-empty ones.
- Whether `meta.output_format_category` should drive tool_result rendering (e.g. `md`
  results rendered as markdown).
- Whether knowledge-block `links` lists deserve rendering or stay preserved-only.
- Memory-file identity for tagging/FTS: `path` is the natural key; the open-set taxonomy
  means the viewer must not enumerate directories.
- Whether the manifest's `export_url` values (live signed links) warrant a "don't commit
  your manifest anywhere" note in user-facing upload help.
- Timestamp-form tolerance: the parser already accepts both ISO forms, but any new code
  must not assume one form per level (the forms moved between formats).
