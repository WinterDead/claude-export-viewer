real browser. The Phase 4 tests pinned the card's HTML as "collapsed by default" and
passed — so the test measured a layer the page doesn't behave at. Reproduce first,

report. Hypotheses, in likely order: (a) the page's collapsible behaviour is wired by JS

markup's "collapsed" attribute has no effect; (c) the template emits an `open`

## Phase 2 — dark mode

Design, ratified in chat:

- **Default follows the system** (`prefers-color-scheme`); a manual override control in
  the nav tail, after Help, with the §C4 copy: label `Theme`, options `System`, `Light`,
  `Dark`.
- **Persistence by cookie** (`viewer_theme`; values `system`/`light`/`dark`; no
  expiry drama — a year is fine), so the server renders the correct theme class on the
  `<html>` element and there is no flash of the wrong theme. No localStorage. The cookie
  is local, first-party, and disclosed in help (§C5).
- **Tokens, not per-element overrides**: extend the existing custom-property set per the
  Session R Phase 2 theming lens — the ~66 hardcoded declarations become the additional
  tokens that lens estimated, including the Phase 3 grey degraded-banner palette and the
  four banner colourways. Two token sets (light and dark) selected by the theme class,
  with `prefers-color-scheme` applying the dark set only under `system`.
- **highlight.js**: vendor a dark theme stylesheet alongside the light one (no CDN,
  ever); load both and select by theme class, or scope the dark rules under the class —
  either way the asset-include test matrices and the licence/vendoring notes are updated
  in lockstep (this is the one test-pinned contract the review said the work touches).
- **Print stays light**: the additive light-token reset inside the `@media print` block,
  as the review specified, so PDF output is unaffected by the active theme. Pin it with a
  test that the print block resets every dark-varying token.
- **Screenshots and footer rules unchanged**; the theme control must be suppressible at
  capture time like the footer.
- Tests: theme class resolution from cookie and absence; control renders and posts
  through its real form; cookie set on choice; print reset coverage; asset matrices.

## §A — Design record amendments (verbatim)

**A1 — append to §2 (Container detection):** `Mixed submissions are refused by design. A
load that combines a legacy archive with current-format category files raises a format
error; the record defines no semantics for the mix because no real export produces one.
The user-facing message is Appendix C11.`

**A2 — replace the "Duplicate categories in one submission: last file wins, with a
warning" sentence in §4 with:** `Same-category files in one submission are first tested
as parts: when the manifest (if supplied) assigns them distinct part numbers, or failing
that when their filenames carry distinct -NNN part suffixes, they merge in part order
through the §3 multi-part merge — content still decides what each file is; part order is
metadata only the manifest and the filename carry. Same-category files not
distinguishable as parts: last file wins, with a warning (the accidental double-pick
guard). Provisional, with §3, until a real multi-part export is observed.`

**A3 — Appendix C11 (mixed-container error):** `Legacy and current-format export files
can't be loaded together — upload one export's files at a time.`

**A4 — provisional markers**: in §4 and §5, replace each *(provisional …)* marker on the
upload shape with `(cleared by the operator hand-test of 2026-09-01)`.
