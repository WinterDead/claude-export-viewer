## Task C — graceful startup on an unparseable stored export

### Behaviour

- Scope: the **stored-upload source only** (`cache/active_export.zip`). When it fails to
  parse at startup, log a `WARNING` naming the source and the parse-error summary, leave the
  file exactly where it is, and fall through to the next source in the existing load order.
- If the dev copy (`data.zip`) fails to parse: log the same class of `WARNING` and fall
  through silently — no banner; it is a developer convenience that public users never have.
- Fixture failure remains a raise: the fixture is committed code, and a broken fixture is a
  broken build, not a user condition (structural invariant per the preserve-and-flag rule).
- When the stored upload was skipped for a parse failure, every page shows a persistent,
  non-dismissible banner (visually distinct from the orphan banner) until a successful
  upload replaces the stored file. Banner text, byte-exact:

<!-- VERBATIM -->
Your stored export couldn't be parsed and wasn't loaded. The file was left in place —
upload a replacement from the Upload page to get back to your data.
<!-- END VERBATIM -->

- The existing parse-before-replace upload flow is the recovery path and needs no changes;
  a successful upload replaces the stored file and the banner condition clears with it.

### Tests (this list defines the target state)

1. Corrupt `active_export.zip`, no dev copy → fixture loads; banner present; the corrupt
   file still on disk, byte-identical.
2. Banner appears on at least home, conversations, and help pages in that state.
3. Banner text matches the authored copy exactly.
4. Successful upload from the corrupt state → new export loaded, banner gone, stored file
   replaced.
5. Healthy stored export → no banner (regression guard).
6. The fallthrough logs a `WARNING` naming the skipped source.
7. Corrupt dev copy, no stored upload → fixture loads, no banner, `WARNING` logged.
8. A corrupt-zip test fixture is added under `tests/` for the above; synthetic bytes only.
