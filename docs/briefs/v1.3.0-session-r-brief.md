# Session R Brief — v1.3.0 Discovery + Codebase Review

**Arc**: v1.3.0 — new export format support, dark mode, codebase review.
**This session**: two phases with a hard phase boundary. Phase 1 discovers and documents
the new export format. Phase 2 is a read-only codebase review. No version bump this
session; v1.3.0 is tagged at the arc's close session.
**Session-length experiment**: this brief deliberately carries what would previously have
been two sessions. The phase boundary is the safety valve: if Phase 1 consumes the
session, run the session-end checklist and stop — Phase 2 then runs as its own session
under this same brief. Ending after Phase 1 is a legitimate ending, not a failure.

## Context

Anthropic has changed the data-export format. The emailed download link now delivers a
manifest `.json` listing four separately downloadable category zips —
`light_metadata-000.zip`, `projects-000.zip`, `memories-000.zip`,
`conversations-000.zip` — replacing the single-zip export the app was built against. The
memory system also changed: what the app supports is now called the Legacy Memory System,
and the new system exports a different structure. v1.3.0 adds support for the new format
while keeping legacy-format support. The renumbering from "1.2.6" to "1.3.0" is a
ratified decision: a whole-archive format change is a minor version by this project's
semver rhythm, and the reserved patch series keeps its role under the name "1.3.x".

A chat-side aggregate scan of a real new-format export (2026-08) produced the findings in
the verification table below. **Treat every row as a verification target, not a
premise** — reproduce independently through the scanner built in Phase 1, and record
confirm/diverge per row. Divergence is a finding, not a failure.

## Ground rules

- **This is a real-data session.** All contact with `data/export-2026-08/` goes through
  the aggregate-only pattern: stdlib-only scanning; every emitted value is a count, a
  type name, a key name, or a length/size statistic. Content strings are touched only by
  `len()`. Verbatim values may be printed **only** for allowlisted machine-enum fields:
  `type`, `sender`, `category`, `part`, `batch_index`, `method`, `tool_origin`,
  `output_format_category`, `resource_type`, `search_provider`, `content_type`,
  `citations_grouping_mode` — and only when the value matches a machine-enum shape
  (short, no spaces beyond single words, no sentence punctuation). Everything else —
  names, titles, emails, IP addresses, filenames from user data, memory-file slugs below
  the top-level directory, message text — is never printed, not even truncated.
- **Mask UUID-shaped strings everywhere they appear, including as dictionary keys.**
  (Lesson from the chat-side scan: `project_memories` is a dict keyed by project UUID,
  and a naive profiler prints those keys as part of the path.)
- `login_history.json` is a new sensitive surface: IP addresses, login timestamps, user
  agents. Aggregates only, same as everything else — and add `ip_address` and `login` to
  the patterns you eyeball at session end alongside the standing step-5 grep.
- Nothing from the real export enters committed files. Every example in the schema doc is
  synthetic, written fresh — never copied-then-edited from real output. Schema docs get a
  human read before commit; they are historically the riskiest doc class in this repo.
- Do not cite pre-remediation commit hashes anywhere, in any committed file. The repo's
  history was rewritten after v1.2.5; old hashes are dead handles and committed docs must
  not advertise them. Identify the baseline by tag name (`v1.2.5`) only.
- Commits authored as WinterDead; the human is "the operator" in all committed prose; no
  real names, paths outside the repo, or machine names.
- GitHub: unauthenticated public reads only. No replies, labels, closures, or any other
  account action — those are operator-only, always.

## Phase 1 — new-format discovery

### 3. Build the scanner: `tools/scan_export_schema.py`

A committable, stdlib-only, aggregate-only schema profiler, useful to any user of the
public repo and to every future format shift. Requirements:

- Input: a path containing either a legacy single-zip export **or** a new-format set
  (manifest plus category zips, any subset present). Tolerate multi-part category files
  (`conversations-001.zip`, …) by scanning all parts of a category; the sample archive
  has only `part 0`, so multi-part handling is structural tolerance, not a verified
  behaviour — say so in its docstring.
- Output: per JSON document, a schema profile — every path, its observed types with
  counts, optional-key presence ratios for dicts, min/max/avg lengths for strings and
  lists — plus value censuses for the allowlisted enum fields above.
- Privacy by construction: the allowlist and the UUID-masking (values **and** dict keys)
  live in the scanner, not in operator discipline. A value that fails the machine-enum
  shape check prints as a masked placeholder with its length.
- Test it against the built-in synthetic fixture (legacy format) first; then run it
  against `data/export-2026-08/`.

## Phase 2 — codebase review (read-only)

The only file this phase writes is its report. Any fix, however small, routes to chat as
a recommendation — no drive-by changes. Crawl the full tree with these lenses:

1. **Dual-format readiness.** Is there a clean parse→internal-model boundary such that
   both container formats can normalise into one model, leaving render, FTS, tagging,
   export, print, and inspect format-agnostic? Name the modules and seams; identify every
   place a container assumption leaks (single zip, fixed filenames, `cache/` paths,
   upload flow, fingerprinting).
2. **1.4+ readiness.** Tag-state isolation (how hard is portable, mergeable tag state
   against the current `viewer.sqlite` layout?); artifact-extraction touchpoints.
3. **Theming readiness.** CSS inventory for dark mode: hardcoded colours, inline styles,
   custom-property usage, how the vendored highlight.js theme is wired, and whether print
   CSS is isolated enough to stay light regardless of theme.
4. **Test architecture.** Coverage map against the standing rules (every UI feature has a
   real-rendered-form test; driven passes name the layer measured); fixture organisation
   ahead of a second format's fixture set; suite runtime.
5. **Dependencies and hygiene.** Cap posture per the procedures; `pip-audit` in a scratch
   venv (dev tool, never a shipped dependency); ruff/black state; dead code; TODO census.
6. **Docs claim-check.** README and in-app help claims against current behaviour — the
   claim-checking pass that verifies docs the way tests verify code. Note claims the new
   format will invalidate (e.g. "upload the ZIP exactly as downloaded").

Report findings ranked: **(a)** blocking for v1.3.0; **(b)** worth fixing during v1.3.0
while the area is open anyway; **(c)** 1.4+/queue material; **(d)** note-only. Each
finding: observation, evidence (file and line), recommendation, rough effort. The
implementation brief will be drafted against this ranking.
