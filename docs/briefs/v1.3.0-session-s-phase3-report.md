Date: 2026-08-25. Phase 2 closed with its own checklist pass (commit "v1.3.0 Session S
Phase 2: …", pushed).

## What shipped

1. **Multi-file upload and inspect (record §4).** Both pages carry one multi-file input
   (`export_files`, `.zip` + `.json`, `multiple`). Each file is sniffed by content
   (`sniff_container`/`sniff_manifest` from Phase 2) and slotted into its kind;
   duplicate kinds in one submission: last file wins with a logged `WARNING`; a
   manifest-only submission is rejected; an unrecognised file errors naming the file.
   The parse-before-replace pattern is generalised to sets: the submission stages into
   `cache/active_export.stage/`, parses, and only on success swaps in as
   `cache/active_export/`. Inspect keeps its no-trace rule — the set is read and parsed
   entirely in memory (`load_export_from_bytes_set`), snapshot-pinned.
2. **Set storage, fingerprint, history, startup (record §5).** The active export is now
   the set directory holding the files as received (manifest included); a legacy ZIP
   upload is a set of one through the same code path, and the route retires any pre-set
   `active_export.zip` on success. A pre-set `active_export.zip` from an earlier
   version is still picked up by the startup load order (step 2 — migration by
   tolerance). `viewer.cache.set_fingerprint` implements the record's fingerprint
   (plain file SHA-256 for a set of one; SHA-256 over sorted per-file digests
   otherwise); it keys the parse cache (`load_or_build` now takes a file or set
   directory), the history rows (existing `zip_sha256` column, no schema change), and
   startup dedup. History filename column: the set summary (`5 files: conversations,
   projects, memories, light_metadata, manifest`); a lone legacy archive keeps its
   filename.
3. **Cap knob (record §4).** `VIEWER_MAX_UPLOAD_MB`, read at startup, default 200,
   junk/non-positive values warn and fall back. Enforced per file server-side while
   staging (upload) and while reading (inspect); the page hint renders the configured
   value; Flask's `MAX_CONTENT_LENGTH` becomes a request-level backstop of five
   per-file caps (one full set: four category zips + manifest). The stale "~11 MB"
   comment is replaced with the record's rationale.
4. **Degraded-view banner (record §4, copy C1 verbatim).** Persistent whenever the
   *viewed* set is missing categories: the lead line, one authored line per missing
   category, and — when a manifest was supplied — `The manifest lists {m} files; {k}
   were supplied.` The banner follows the view (an inspected subset is described as
   truthfully as the active one); the manifest status survives restarts because the
   stored manifest is re-read from the set directory at startup.
5. **Tests.** 24 new cases (`tests/test_upload_sets.py` plus a set-input no-trace case
   in `test_inspect.py`), all through the **real rendered form** — field name,
   multiplicity, and accepted types scraped from the page, never hand-built. States:
   full set with and without manifest, single-category subset, manifest+subset
   (mismatch line), manifest-only (rejected), duplicate category (last-wins), legacy
   set-of-one (filename + plain-sha continuity), unrecognised file, failed-second-upload
   (previous set intact on disk and in memory), cap knob parsing and both routes'
   per-file enforcement, request backstop, startup pickup/dedup/summary-after-change,
   set-of-one dedup against a **pre-existing** single-zip history row, corrupt stored
   set fallthrough with banner, inspect subsets with banner and exit, and
   `summarise_set` shapes.

Suite at close: **635 passed**, ruff clean, black clean.

## Disclosed judgment calls

- **§4 vs §3 tension: duplicate categories vs multi-part.** §3 says multi-part
  categories merge; §4 says a duplicate category in one submission is last-wins. Two
  parts of one category are indistinguishable *by content* from an accidental
  double-pick, and filenames never decide parsing — so the two rules collide for a
  genuine multi-part upload through the UI. Implemented: **the letter of §4 at the
  routes** (last-wins with a warning), because no multi-part export has been observed
  and §4's protection against accidental double-picks is the operative intent today;
  the loader-level merge (§3) remains implemented and tested for directory loads.
  **Surfaced for the operator**: when a real multi-part export appears, the upload flow
  needs a ruling (e.g. same-category files with distinct part numbers merge; identical
  category otherwise last-wins).
- **Fingerprint covers the manifest.** The set is "the supplied files as received", so
  the manifest participates in the set identity; re-uploading the same zips with vs
  without the manifest is a different set. Set-of-one continuity is unaffected.
- **Superseded pre-set zip is removed on successful upload.** After the new set swaps
  in, a leftover `active_export.zip` would silently resurrect an old export if the set
  directory were ever hand-deleted; the upload's "replace" semantics argue for retiring
  it. Startup never removes it (tolerance only).
- **`MAX_CONTENT_LENGTH` multiplier.** Per-file enforcement can't ride Flask's
  request-level limit any more (a valid 4-zip set exceeds one per-file cap), so the
  request limit became a 5× backstop and the exact rule moved into the staging loop.
  Both record-named enforcement sides survive: the page hint (client) and server
  rejection.
- **Knob name kept.** No existing environment-variable convention was found in the
  codebase (this is its first env knob), so `VIEWER_MAX_UPLOAD_MB` stands as the
  record names it.
- **Flagged copy (operator review requested).** The record's appendix carries no words
  for these small surfaces, so minimal factual strings were drafted in the existing
  voice: the upload page's lede/hint updates (multi-file, set directory path,
  per-file cap), the inspect page's label/hint (its authored Session K intro is
  untouched), and three new error strings — "Files must be .zip archives or a manifest
  .json.", "The manifest alone doesn't contain your data — include the export .zip
  files as well.", "*{file}* isn't a recognised export file.", plus "*{file}* exceeds
  the *{n}* MB per-file cap." The graceful-startup banner's authored copy ("The file
  was left in place…") is deliberately untouched even though the stored export can now
  be a set — still truthful, and its bytes are test-pinned.
- **Behaviour change: malformed zips now fail at detection.** A corrupt `.zip` errors
  as "*{file}* isn't a recognised export file" (named, per-file) rather than the old
  "Couldn't parse archive"; two existing tests were updated to the new message.
- **Banner palette.** The degraded banner is a fourth, neutral-grey palette beside the
  amber/red/blue banners; hardcoded colours join the dark-mode token sweep already
  scoped for Session T. A visual pass of the banner is left to the Phase 4 operator
  hand-test brief — a browser file picker can't be driven programmatically, and the C1
  copy is byte-pinned by tests.
- **Test-run hygiene incident, resolved.** The first Phase 3 test run wrote
  `cache/active_export/replacement.zip` (synthetic fixture bytes) into the repo's real
  `cache/` because `test_startup.py`'s fixture didn't yet patch the new `ACTIVE_SET`
  global. The artefact was removed, the fixture now patches `ACTIVE_SET`, and the
  shared `app_factory` patches it for every other module. `cache/` is gitignored;
  nothing real was touched and nothing was committed.
