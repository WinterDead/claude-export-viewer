# Claude Export Viewer — v1.1 Session G Brief

Read CLAUDE.md and docs/plan.md before doing anything else.

This is the final v1.1 session: README, LICENSE, screenshots, version bump, and the v1.1.0 tag. It runs in **two phases with a mandatory hard stop between them** — Phase 1 produces drafts; nothing is committed until the drafts have been reviewed in chat and approval comes back. Gate language as established: soft gate = resolve-and-flag; hard stop = end the phase and report.

## Phase 1 — produce drafts, then stop

### G1. README.md

Draft a top-level README for a general public audience. The repo is private today and goes public at v1.2 — write for the public state. Structure:

1. **Title and pitch** — one short paragraph: a local web app for browsing your Claude data export (conversations with full branch history, projects, memory), with project tagging, full-text search, and upload history. Lead with the privacy property: everything runs on your machine; nothing is uploaded anywhere.
2. **Screenshots** — 3 or 4, per G2.
3. **Features** — concise list: conversation browsing with branch navigation; project pages with knowledge docs and custom instructions; the tagging system and triage workflow (Untagged / projects / No Project); memory rendering with collapsible sections; FTS5 full-text search with a built-in syntax guide; upload history; syntax-highlighted code blocks; in-app help.
4. **Privacy and scope** — its own section, stated plainly: local-only, no telemetry, no network calls at runtime, all data stays in the project's `cache/` folder. Be honest about scope: this runs Flask's development server bound to 127.0.0.1 — it is a personal local tool, not a hosted service, and should not be exposed to a network.
5. **Quick start** — the launcher path first (download/clone; Windows: double-click `run.bat`; macOS/Linux: `./run.sh`; requires Python 3.11+, with the python.org pointer), then the manual path (venv, `pip install -e .`, `flask --app app run`) for people who prefer it.
6. **Getting your export** — three or four sentences condensed from the help page's section, ending with a pointer to the in-app Help page for everything else.
7. **Development** — tests (`pytest`), lint/format (`ruff`, `black`), and a pointer to `docs/` (the export schema, the artifact-encoding study, the plan).
8. **Licence** — one line referencing the LICENSE file.

Constraints, all inherited from the established copy rules: Canadian English; general audience; no personal paths, usernames, or machine details; **every behavioural claim verified against the code before the draft leaves Phase 1** (the README gets the same verified-documentation status as the help page and search guide — note verification in the draft report, stop-and-surface any claim that doesn't hold). Don't oversell: no superlatives, no comparisons to other tools by name.

### G2. Screenshots

- Source: **the synthetic fixture only**, per the locked plan rule, with the footer avoided or cropped (it echoes the local source path verbatim).
- Take them from an **isolated app instance** — a temporary cache/working directory or equivalent. Hard stop if isolation isn't achievable without touching the real `cache/`: the real active export, tag database, and history must not be moved, modified, or risked for screenshots.
- Suggested set: the conversations list (showing tags and the filter), a conversation detail at a branch point (switcher visible), search results with highlighted hits, and the help page partially expanded. Store under `docs/images/` and reference from the README.
- **Soft gate on presentability:** the synthetic fixture is deliberately placeholder-flavoured. If the screenshots read as gibberish rather than as an honest small demo, don't polish the fixture in this session — include the screenshots in the Phase 1 report with a note, and the review will decide between shipping them and scheduling a purpose-built demo fixture before the public flip.

### Phase 1 report

Deliver: the README draft in full, the screenshots (or their paths plus descriptions), the claim-verification notes, and any soft-gate flags. **Then stop. No commits, no version bump, no tag.**

## Phase 2 — on approval from chat

1. Apply any edits from the review verbatim.
2. Commit README, LICENSE, screenshots.
3. Bump the project version metadata (pyproject) to `1.1.0`.
4. Update docs/plan.md: Session G shipped; v1.1 closed; carry the v1.2 gate-item list forward unchanged (public-readiness audit, artifact extraction pending the branch-semantics decision, the file-tools discovery pass).
5. Run the full session-end checklist — both privacy greps, plus a final pass of the GitHub-rendered (or locally previewed) README for layout problems.
6. Tag `v1.1.0` (annotated), message summarising the version in a few lines.

One explicit non-goal, to head off end-of-version temptation: no drive-by fixes, no backlog items, no "while we're here." The sort-vocabulary polish and graceful-startup items stay unscheduled. v1.1 closes exactly as scoped.
