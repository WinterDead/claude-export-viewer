## Task A — launcher hardening

Background (operator-verified on a Linux Mint 22.2 live session, 2026-07): fresh
Debian-family systems ship Python without the venv module, so `python3 -m venv` fails with
a raw ensurepip error (**B1**); that failure leaves a `.venv/` with no pip in it, which the
scripts then trust on rerun and die with "No module named pip" (**B2**).

A1. **`run.sh`, B1**: detect venv-creation failure. On failure: remove the partial `.venv`
just attempted, print the following, exit non-zero.

<!-- VERBATIM -->
This system's Python can't create virtual environments yet — the add-on that provides
them is missing. On Ubuntu, Mint, or Debian, run:

    sudo apt update && sudo apt install python3-venv

then run this script again. On other systems, install the venv module for your
Python 3.11+ and rerun.
<!-- END VERBATIM -->

A2. **`run.sh`, B2**: before trusting an existing `.venv`, probe
`.venv/bin/python -m pip --version`. On failure, print the line below, remove and recreate
the venv (which re-enters the A1 handling if creation fails again), and continue normally.

<!-- VERBATIM -->
The app's virtual environment is incomplete — rebuilding it...
<!-- END VERBATIM -->

A3. **Windows mirror check** (`run.ps1`; `run.bat` shims into it): *verify, don't assume*
whether the same two gaps exist — venv-creation failure surfacing raw, and an existing venv
trusted without a pip probe (`.venv\Scripts\python.exe -m pip --version`). Fix whichever
exist in the same shape, reusing the A1/A2 copy with only mechanical path adaptations
(soft gate). The existing Store-stub detection branch is out of scope — don't rework it.

A4. **Tests**: launcher logic isn't directly pytest-runnable, so extend
`tests/test_launchers.py` with content guards — the scripts contain the pip probe, the B1
message marker text, and the rebuild notice — plus the existing presence/wiring/
verify-negative guards still passing.

## Task B — explicit host binding

Session I's tripwire verified that every start path binds 127.0.0.1, but only via the
installed Flask CLI's Click default — nothing in this repo states it. Explicit beats
implicit for a security property:

B1. Add `--host 127.0.0.1` to the `flask run` invocations in `run.sh`, `run.ps1`, and
`.claude/launch.json`, and to the manual-command line printed by the all-busy port message
(that line is launcher copy, ours to edit).

B2. **Non-goal, explicit**: the manual commands in README.md and help.md stay as they are —
they inherit Flask's localhost default, and editing them is public-voice work this session
must not do.

B3. **Tests**: content guards that the three files above carry the flag, plus a canary test
that fails if the installed Flask CLI's `run` default host ever stops being
127.0.0.1 — so the README/help commands' implicit safety is continuously checked at dev
time.

## Task C — secret-key handling

Verify how the Flask `SECRET_KEY` (required by Flask-WTF's CSRF) is currently established —
this is a verification target, not a stated premise. Three anticipated buckets:

- **Hardcoded literal committed in the repo** → replace with per-start
  `secrets.token_hex(32)` (target state below).
- **Already random per-process** → confirm mechanism quality and pin with a test.
- **Read from environment with a committed fallback literal** → replace the fallback with
  the per-start random value; keep the env override.

Target state: a fresh random key per app start (`secrets` module). Consequence — CSRF
tokens don't survive a restart — is accepted for a localhost single-user tool (operator
decision). Pin with a test (mechanism presence and key strength; implementation Code's
choice). **Anything outside these buckets is a hard stop.**
