### A2 — the Werkzeug spool item (Session K's recorded audit input)

Behaviour, verified against the installed code: every multipart upload (Upload and Inspect
POSTs) is parsed by Werkzeug's form parser, whose `default_stream_factory`
(`werkzeug/formparser.py:53-66`, v3.1.8) writes each part to a
`SpooledTemporaryFile(max_size=1024*500)` — in memory up to 500 KB, rolled over to an OS
temporary file beyond that. Export archives are megabytes, so upload bodies do transit an
OS temp file during request parsing. Deletion: Flask's request-context teardown
(`flask/ctx.py:422-424`, v3.1.3) calls `Request.close()`
(`werkzeug/wrappers/request.py:301-310`), which closes every `FileStorage`; closing the
rolled `SpooledTemporaryFile` closes its underlying `tempfile.TemporaryFile`, which the OS
deletes on close by construction (`O_TEMPORARY` on Windows; pre-unlinked on POSIX). The
deletion claim holds in the installed stack.

**Verdict on the help copy:** the Inspect section's "nothing saved to disk" remains fair
under an ordinary reading. The app itself writes nothing and nothing persists beyond the
request; the transient spool is a stack-inherent mechanic of every web upload, engineering
around which would be a stack change (Session K hard stop, unchanged). Documented here as
the brief required; no fix applicable.

### B3 — the "dead attachment toggle" (no code defect; root-caused; e2e tests added)

**Reproduction, as the brief demanded, through the real rendered form.** The brief's first
hypothesis (duplicate query parameters; server reads the hidden 0 first) is not what
ships: the template deliberately puts the checkbox **before** its hidden-0 fallback, and
both endpoints read the **first** value (`request.args/form.get` on a Werkzeug MultiDict
returns the first; verified directly). Empirically, with browser-order serialisation of
the actual markup — and separately in a driven Chromium clicking the real Export button —
all four checkbox states are honoured on all three surfaces (single export, Copy fetch,
bulk POST): ticked attachments produce `attachments: included` plus the attachment text;
unticked produce `attachments: referenced` plus `— text not exported.`; same for thinking
(`[Thinking]` present/absent). The driven browser submitted
`?thinking=1&thinking=0&attachments=1&attachments=0` — checkbox values first, exactly as
designed.

**Root cause of the operator's observation — a reach mismatch, not a form bug.** The
export model distinguishes *attachments* (pasted-text attachments with extracted content —
what "Include attachment text" governs) from *files* (binary uploads, name-only in the
archive, **never** included, by design: `> **[Files]** N binary file(s) attached (not
included in export)`). An aggregate census of the real archive (counts only, no content):
**7 of 213** conversations carry text attachments — all 7 alongside binary files — while
**41** carry binary files (34 files-only). A conversation picked for "attachments" is
therefore ~5× more likely to show only the files notice, which no toggle can change and
which reads exactly as "reference-only regardless". On the 7 mixed conversations the
attachment text does toggle, but the files line stays either way.

**Fix applied:** none to the endpoints — "read the last value" would *break* the shipped
checkbox-first markup, and restructuring the pair mechanism would be behaviour-neutral
churn. What the bug report actually exposed (the meta-gap) is closed:
`tests/test_export_form_e2e.py` submits the template's real rendered markup through a
browser-faithful serialiser (tree order, successful controls only) for **all four
checkbox states** on the Export, Copy (`frontmatter=0`), and bulk-form paths — 12
parametrised cases plus the grouping pin. Hand-built-parameter endpoint tests can no
longer mask a form-level regression.

**Reported for operator judgment (hard stop on copy changes):** the label "Include
attachment text" invites the everyday reading of "attachment" that includes binary file
uploads. A one-line clarification near the toggle or in help.md would close the trap, but
user-facing copy beyond Task B's specified edits is out of this session's gates.

### B5 — the links appendix (mechanism verified working; operator observation root-caused; guards added)

**Reproduction in real print rendering.** Against a link-bearing fixture (the synthetic
fixture with markdown links added to a conversation — the committed fixture has none), a
real printed PDF via headless Chromium shows the feature working end-to-end: inline
`[1]`/`[2]` markers after link text, repeated URL sharing one number, and the "Links"
section at the end with `N. <text> — <URL>` entries. The browser's parsed CSSOM confirms
all 16 `@media print` rules intact, and the equal-specificity cascade resolves correctly
(the print reveals come later in the sheet than the screen-side `display: none`). None of
the brief's candidate causes exist: class names match between JS and CSS, the script is
loaded on the template, `beforeprint` is wired, and the selector scope matches the
rendered markup.

**What Session N's pass actually measured** (from its own report, "In-session browser
pass"): the synthetic fixture only — which contains **zero** links — with test links
**injected into the DOM**; it verified the JS built markers and appendix, dedup numbering,
closed-section exclusion, and that on *screen* both compute `display: none`. **It never
rendered print output.** Its "confirmation" was of the JS/DOM layer; the print-reveal
layer went unverified until now (it happens to work).

**Root cause of the operator's observation — link-form reach.** The appendix covers
`<a href>` anchors, i.e. markdown-form links; the renderer's extensions (`fenced_code`,
`tables`, `sane_lists`, `nl2br`) do not autolink bare URLs. Aggregate census of the real
archive (counts only): **99 of 213** conversations carry bare `http(s)://` URLs in visible
text; only **12** carry markdown-form links; **91** carry bare URLs with *no* markdown
link anywhere. On those 91, the page shows URLs but contains no anchors, so the appendix
correctly builds nothing — no markers, no Links section, exactly the operator's
observation. Worth noting: a bare URL already prints its own full address inline, so for
those conversations the appendix would add no information — the design's purpose (recover
the href a printed page loses) doesn't arise.

**Fix applied:** none to the JS/CSS — nothing is broken there. Pinned with the content
guard the brief specified:
`tests/test_export_ui.py::test_print_links_js_class_names_match_print_css_reveals` ties
the class names the JS assigns to the screen-hide and print-reveal rules (including
cascade order and the hide-list exclusion), so neither side can drift silently.

**Reported for operator judgment (hard stop):** if lived use wants bare URLs to
participate (clickable on screen and/or listed in the appendix), that is a rendering-stack
decision — e.g. a linkify pass — which changes screen output globally and touches the
sanitiser pipeline's surroundings. Queued as an input to the existing 1.2.6+
link-appendix-toggle item; see "remaining before flip".
