## A2. Search syntax guide

**Rationale:** the current one-line tip names the operators without explaining what problem each solves. Users (including the developer) can't apply them from the tip alone.

**Spec:**

- Replace the current tip with: (a) a short always-visible line, and (b) a collapsed native `<details>` block titled "Search syntax guide" directly beneath the search input.
- The details block is present in all three search-page states: empty query, results shown, and syntax-error. The error state is where it's needed most.
- Server-rendered, no JavaScript. Style consistent with the app's existing collapsible patterns.
- The copy below is final (Canadian English, reviewed). Adapt the markup (headings, `<code>`, bold) to the template; do not rewrite the wording. If a claim in the copy contradicts actual FTS5/preprocessor behaviour when you verify it, stop and surface the discrepancy.

**Always-visible tip line:**

> Just type what you're looking for — punctuation, apostrophes, and hyphens are handled automatically. For advanced operators, open the syntax guide below.

**Details block copy:**

---

**The default: plain words.** Type words like you would in any search box: `flask sqlite tagging`. Every word must appear somewhere in the result, but not necessarily together or in order. Punctuation is safe — `don't`, `B.Sc.`, and `covid-19` all work as-is.

**"Exact phrase" — words together, in order.** Wrap words in double quotes to match them as a unit. `"branch point"` finds only places where those two words sit side by side; without quotes, they could be paragraphs apart.
Example: `"upload history"` — matches the phrase, not scattered mentions of uploads and history.

**prefix\* — match the start of a word.** Put an asterisk at the end of a word stem to match every word beginning with it.
Example: `electr*` matches electric, electrical, electronics, electron.
The asterisk only works at the end of a word — `*lectric` won't.

**NEAR(a b, N) — words close together, any order.** Matches when the terms appear within N words of each other, in either order. Useful when you remember the concept but not the phrasing.
Example: `NEAR(memory project, 8)` matches "project memory," "memory for this project," and similar.
If you leave off the number — `NEAR(memory project)` — the distance defaults to 10.

**AND, OR, NOT — combining and excluding.** These must be uppercase; lowercase and/or/not are treated as ordinary search words.

- `flask AND sqlite` — both must appear. (This is already the default between plain words.)
- `flask OR fastapi` — either one is enough.
- `python NOT snake` — has python, doesn't have snake. NOT sits between two terms. There is no leading-minus exclusion — `-snake` is treated as an ordinary word, which is why searches like `covid-19` keep working.

**( … ) — grouping.** Parentheses make combinations unambiguous.
Example: `(flask OR fastapi) AND sqlite` — sqlite, plus at least one of the two frameworks.

**Mixing operators with ordinary words.** The moment a query contains any operator, the whole query switches to strict syntax mode — punctuation is no longer handled for you. Quote anything with apostrophes, periods, or hyphens:
`"B.Sc." AND engineering` works; `B.Sc. AND engineering` is a syntax error.

**Putting it together.** `("export viewer" OR archive) NOT readme` — finds export-viewer or archive content while skipping anything that mentions readme. When combining different operators, use parentheses rather than relying on precedence rules.

**What's searched:** conversation titles and summaries, every message (including messages on alternate branches), project names and descriptions, knowledge documents, and all memory blobs.

## A3. Upload history log

**Rationale:** a record of what exports have been loaded, when, and what they contained. Doubles as an archive-growth view.

**Spec:**

- New table `upload_history` in the existing `cache/viewer.sqlite`, created via the same `CREATE TABLE IF NOT EXISTS` scaffolding pattern as the tag table. Columns:
  - `id` INTEGER PRIMARY KEY
  - `recorded_at_utc` TEXT (ISO 8601)
  - `source` TEXT — `'upload'` or `'startup'`
  - `filename` TEXT — the original uploaded filename for uploads; the basename of the loaded path for startup loads
  - `zip_sha256` TEXT — reuse the sha256 already computed for the pickle-cache key; do not hash the file a second time
  - `conversations`, `messages`, `projects`, `project_memories` — INTEGER counts taken from the successfully parsed export
- Record **after successful parse only** (the parse-before-replace flow already exists; hook after success).
- **Upload route:** always record, even if the sha256 matches an earlier row — a UI upload is an explicit user action worth logging.
- **Startup loads:** record only when loading a real export (`cache/active_export.zip` or `data/data.zip`) **and** the sha256 differs from the most recent history row. This prevents a duplicate row on every app launch. Synthetic-fixture loads record nothing.
- **`/history` page** with a "History" link in the top nav: a reverse-chronological table showing when (relative time, absolute timestamp in a title attribute), a source badge (Upload / Startup), filename, the four counts, and a short sha (first 12 characters, full hash in a title attribute). Empty state: a friendly one-line "No uploads recorded yet" message, styled like the app's other empty states.
- No migration concerns (new table), but follow the house preserve-and-flag pattern for anything unexpected.

**Tests:**

- Upload records a row with correct counts.
- Startup with the same sha as the latest row: no new row.
- Startup with a different sha: new row recorded.
- Synthetic-fixture load: nothing recorded.
- `/history` renders rows in reverse-chronological order; empty state renders when the table is empty.

**Deliverable:** a scenario table — columns: scenario, expected rows recorded, page behaviour.
