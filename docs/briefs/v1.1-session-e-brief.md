## E1. Launcher scripts

Three files at the project root:

- **`run.ps1`** — the real Windows logic.
- **`run.bat`** — a one-line shim so double-clicking works without execution-policy friction: invoke PowerShell with `-ExecutionPolicy Bypass -File run.ps1` (scoped to this invocation only; do not change any system or user policy).
- **`run.sh`** — the POSIX equivalent (bash, macOS/Linux), `chmod +x`, with a portability shebang.

### What a run does, in order

1. **Find a suitable Python (3.11+).** On Windows, try the `py -3` launcher first, then `python`; detect and reject the Microsoft Store stub (the alias that opens the Store instead of running Python). On POSIX, try `python3`, then `python`. Verify the version meets the project's minimum.
2. **If no suitable Python:** print a friendly, specific message — what was looked for, what was found (nothing / too old / Store stub), and that Python 3.11 or newer is needed from https://www.python.org/downloads/ — including the Windows tip to tick "Add Python to PATH" during install. Exit cleanly; do not attempt to install anything on the user's behalf.
3. **Create `.venv` if absent** and install the project into it (`pip install -e .`). If `.venv` exists, skip creation; the script must be idempotent — every run after the first is effectively activate-and-launch.
4. **Pick a port.** Probe the default (5000); if busy, fall through a short list (5050, 5051, 5052) and print which port was chosen. If all are busy, say so and exit with the manual `--port` instruction.
5. **Launch the app and open the browser** at `http://127.0.0.1:<port>`. Print that Ctrl+C in the window stops the app.

### Constraints

- Scripts are part of the public-facing first impression: messages in plain language, no personal paths, no assumptions about drive letters or directory names — everything relative to the script's own location.
- No network access except pip's normal dependency installation. The scripts must never change system state outside the project folder (no PATH edits, no policy changes, no installs beyond the venv).
- Failure messages always end with what the user should do next.

## Tests and verification

Shell scripts don't unit-test well in this project's pytest setup, so verification is a **manual matrix**, run on the dev machine and recorded in `docs/briefs/v1.1-session-e-verification.md`:

| Scenario | Expected |
| --- | --- |
| Fresh state (rename `.venv` away), double-click `run.bat` | venv created, deps installed, app launches, browser opens |
| Second run (venv present) | fast path: no reinstall, app launches |
| Port 5000 occupied (start a dummy listener) | falls through, prints chosen port, browser opens on it |
| Python missing (simulate: temporarily shadow PATH in a child shell) | friendly message with python.org link, clean exit |
| `run.sh` syntax | at minimum `bash -n run.sh`; full run if a POSIX environment is available, otherwise note it as verified-syntax-only |

Automated where cheap: a pytest asserting the three files exist, `run.bat` references `run.ps1`, and the scripts contain no drive-letter paths or usernames (same verify-negatives spirit as the help page).

Soft gate: if the Flask dev-server invocation needs an adjustment to behave well when launched from the script (working directory, env), make it and flag it. Hard stop: any change to app code beyond that launch path — launcher polish must not become app refactoring.
