## Findings

- **F1 — V7 not exercised.** The ordering and active-version cautions are design-safe
  (§6.1 sorts by `created_at` and marks the active version wherever it falls) but untested
  by real data; the synthetic multi-file artifact exercises both.
- **F2 — V17's "two of three" counted prose mentions.** With the record's §6.5 rule, one of
  three artifacts in the later set is linked (the same artifact is named by both an
  `Artifact` result's `structured_content.artifact_id` and a Docs tool's
  `container.id`); a second appears only in tool-result prose, which §6.5 deliberately
  excludes. Not a contradiction — §6.5 is provisional and its rule stands — but the
  operator should expect "Not mentioned in any conversation in this export." on two of
  three artifacts in that export. A question for the record, not for this session.
- **F3 — `meta.tool_references` is a list of strings** (one to three entries, 10–38
  characters), not dicts. The fixture mirrors that; the viewer does not interpret it.
- **F4 — six `Artifact` tool uses, one result carrying `artifact_id`.** The other calls'
  results carry no structured id. Consistent with V17; noted for the §6.5 revisit.
- **F5 — the earlier set's manifest lists five categories**, so under A7 its banner would
  count against 5, not 7 — correct per the record (expected categories are the manifest's).
- **F6 — timestamp forms** differ per new file (seconds with offset, milliseconds `Z`,
  microseconds with offset, nine fractional digits `Z`); all parse with
  `datetime.fromisoformat`. Fixtures mirror each form.

## Disclosures (four-part)

**G1.1 — `source` was already absent from the allowlist.**
*Observation*: `ENUM_FIELDS` at v1.3.0 contains no `source` key; the chat-side scan that
leaked website names was a different tool.
*Letter*: "Remove `source` from the enum key allowlist."
*Intent*: website names from `display_content.link.source` never print.
*Decision*: nothing to remove; the intent is pinned instead — a verify-negative test asserts
`source` is in neither allowlist and that the fixture's link `source` value never appears in
the output.

**G1.2 — what a "field" is for the cardinality cap.**
*Observation*: the brief caps a field's distinct values "across the scan"; a key name such
as `type` spans unrelated paths (block types, citation types, display types).
*Letter*: "a field is printed as an enum only when its distinct values are few (≤ 12) across
the scan".
*Intent*: no free-form value leaks through an allowlisted key.
*Decision*: a field is one schema path within one document group, pooled across every export
in the scan; the scanner's own check censuses are capped the same way (the real run's
`frames` member-layout census was suppressed at 13 distinct shapes — V3 is verified from the
layout counts instead).

**G1.3 — path-scoped enum allowlisting.**
*Observation*: the new enums (`kind`, `visibility`, `mime_type`, `status`, the manifest
`version`, attachment `file_type`) are common words as keys; tool inputs are an open set.
*Letter*: the brief names the cap but not how new enums enter the allowlist.
*Intent*: print only machine enums.
*Decision*: these enter as exact schema paths (`SCOPED_ENUM_PATHS`) or a path suffix, never
as global keys.

**G1.4 — order of work: fixtures before the first real run.**
*Observation*: the brief lists the scanner, then the real-data reproduction, then fixtures.
*Letter*: steps 1–4 in order.
*Intent*: privacy stays in the tool, verified.
*Decision*: the fixtures and the scanner privacy tests were built first, so the tool's
privacy rules were proven on synthetic data before it touched the real directory.

**G1.5 — the new category ZIPs are not in `current/` yet.**
*Observation*: v1.3.0's loader raises `MixedContainerError` for any unrecognised ZIP beside
category ZIPs, and the shared `export_path` fixture loads `current/` by directory — adding
`frames-000.zip` there now turns most of the suite red.
*Letter*: "`current/` gains `frames-000.zip`, `artifact_data-000.zip`, and
`claude_code_cloud-000.zip`".
*Intent*: the fixtures exist and are exercised, and every phase closes green.
*Decision*: the three ZIPs are built in phase 1 into `current_new_only/` (also the record
§10 "new categories alone" case); phase 3 adds them to `current/` — and the manifest's list
— in the same commit as the A6 tolerance that lets them load.

**G1.6 — conversation additions are current-format only.**
*Observation*: the dual-format fixtures are kept behaviourally parallel.
*Letter*: "The conversations fixture gains …".
*Intent*: exercise V17–V19 shapes, which exist only in current exports.
*Decision*: added to the current-format conv-3 only; conversation and message counts stay
parallel, conv-3's block count differs by format. No existing test depended on that count.

**G1.7 — fixture fidelity corrections from the real profile.**
*Observation*: `meta.tool_references` holds strings; each new file uses its own timestamp
form.
*Letter*: "behaviourally parallel to the observed structures".
*Intent*: fixtures exercise the shapes the loader will meet.
*Decision*: fixtures updated to string `tool_references` and to each file's timestamp form
(including a nine-digit fraction on run start times).

**G1.8 — page file names in the fixture.**
*Observation*: the real `page` artifact's root file names are not structural (one page
artifact), so the scanner masks them and their real names are unknown.
*Letter*: "root Markdown and a comments file".
*Intent*: content decides, filenames never do.
*Decision*: the fixture uses neutral names; the loader (phase 4) must find the content and
comments by layout and extension, never by name.

**G1.9 — legacy login-history variant name.**
*Observation*: the brief asks for "a sibling variant" without a name.
*Letter*: "The legacy fixture gains a sibling variant with `login_history.json`."
*Intent*: a second legacy ZIP, the original untouched.
*Decision*: `synthetic_export_login_history.zip`, registered beside `synthetic_export.zip`.
