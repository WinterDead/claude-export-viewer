# Claude Export Viewer — v1.1 Session D Brief

Read CLAUDE.md, docs/plan.md, and the artifact-related sections of docs/export-schema.md before doing anything else.

This is a **discovery session**. The deliverable is knowledge, not features: a schema-style document plus a go/no-go recommendation on artifact extraction. **Hard stop: no application code in this session.** No parser changes, no routes, no templates, no rendering — if the findings make implementation look easy, that is still a future session. A hard stop means: do not implement, even if the resolution seems obvious; end the session and report instead.

## Background

Conversations in the export contain `tool_use` blocks with `name == "artifacts"` — the viewer currently renders these as placeholder cards. Whether the artifacts themselves are *recoverable* (full content, final state after edits) has never been verified. Creation calls likely carry initial content; subsequent edits likely arrive as update/rewrite commands that would need replaying; large inputs may be truncated in the export. This session establishes the facts.

## Privacy constraints for this session

You will be analysing the real export at `cache/active_export.zip`. Three rules:

1. **Work through scripts and aggregates.** Characterise structure via scanner output (counts, field inventories, length distributions), not by reading conversations wholesale. Read raw content directly only as far as needed to understand structure.
2. **Nothing from the real export goes into any committed file.** Aggregate counts are fine (e.g. "this export contained N artifact tool calls"). Illustrative examples in the documentation must be **synthetic** — write them from scratch to show the shape, never copy real content, titles, or identifiers.
3. The deliverable doc must hold to the general-audience rule like everything else committed.

## D1. Inventory scan

Write a scanner (stdlib-only, operating on the export ZIP) that walks every conversation, every message, **including non-canonical branches**, and inventories all `tool_use` blocks with `name == "artifacts"`. Capture per call:

- Command type (`create`, `update`, `rewrite`, anything else observed)
- Input fields present (id, type/language, title, content, old_str/new_str, version markers — whatever exists)
- Content lengths
- The paired `tool_result` block's structure, if informative
- Conversation/branch position (canonical path vs alternate branch)

Report aggregates: total calls, distribution by command type, artifact types observed (code/markdown/html/react/svg/mermaid/other), artifacts per conversation, how many artifact IDs have multi-command histories.

## D2. Truncation check

Determine whether large inputs are truncated in the export. Look for: content cut mid-structure (unclosed fences, dangling JSON), explicit truncation markers, fields absent on large calls that are present on small ones, and suspicious pile-ups at identical maximum lengths in the length distribution. Report findings either way — "no evidence of truncation" is a result, but state what was checked, per the house verify-negatives spirit.

## D3. Reconstruction feasibility

Select samples covering, where the export contains them:

- (a) a create-only artifact
- (b) an artifact with one or more `update` commands (old_str/new_str replay)
- (c) a `rewrite` chain
- (d) an artifact whose edit history spans a branch point

For each, attempt offline reconstruction in a scratch script: replay the command sequence and report fidelity. Do `old_str` matches apply cleanly? Do replays ever fail, and why? For (d), document what "the final artifact" even means when edits diverge across branches — likely answer: final state is per-branch, resolved along a chosen render path — and lay out the options without choosing one. That choice is a future chat decision.

## D4. The deliverable document

Write `docs/artifact-encoding.md` in the same empirical spirit as `docs/export-schema.md`:

- The observed encoding: block structure, command grammar, field semantics (synthetic examples only)
- Aggregate findings from this export, clearly marked as one-export observations rather than format guarantees
- Truncation findings and what was checked
- Reconstruction results per sample category, with failure modes
- Branch semantics: the problem statement and the candidate resolution rules
- **Recommendation**: feasible / partially feasible / not feasible, and if feasible, a proposed minimal scope for a future implementation session (e.g. reconstruct final state along the rendered path + download button), explicitly deferred to v1.2 planning

## D5. The scanner script

If the scanner ends up generic (operates on any export, no hardcoded values, clean output), commit it under `tools/` with a one-line docstring — it doubles as a re-check utility the next time Anthropic's export format shifts. If it stays scrappy, leave it uncommitted and note that in the summary. Either is fine; say which you chose.

## Deliverables

1. `docs/artifact-encoding.md` as specified.
2. A summary table in the session report: artifact call count, command distribution, truncation verdict, reconstruction success per sample category, and the one-line recommendation.

## Session end

No tests required (no app code — and the hard stop above applies to test scaffolding too). Run the session-end checklist from CLAUDE.md; the privacy grep matters doubly here given the session touched the real export. In docs/plan.md, mark Session D shipped and record the recommendation as an input to v1.2 planning. Do not tag.
