# v1.1 Session E — launcher verification matrix

Manual verification of the launcher scripts (`run.ps1`, `run.bat`, `run.sh`), run on the
Windows dev machine on 2026-06-09 per the Session E brief. Shell scripts don't unit-test well
in this project's pytest setup, so this matrix is the primary evidence; the cheap automatable
checks live in `tests/test_launchers.py` (files exist, the `.bat` shim points at `run.ps1`
with a per-invocation policy bypass, no drive-letter paths or machine usernames, `run.sh`
keeps its bash shebang and LF endings).

Method notes:

- Each Windows scenario invoked `run.bat` through `cmd /c`, the closest scriptable analogue
  to double-clicking it in Explorer.
- "Browser opens" was confirmed from the Flask access log: the launcher's browser job requests
  `/` (followed by the static assets and a favicon probe), while the test harness only ever
  polled the TCP port and fetched `/help` — so a logged `GET /` proves the default browser
  actually opened the page. It did, on the correct port, in every launch scenario.
- The dev `.venv` (which carries pytest/black/ruff) was renamed aside for the fresh-state
  scenario and restored afterwards; the launcher-created venv was deleted once the matrix
  finished.

| Scenario | How it was run | Observed | Verdict |
| --- | --- | --- | --- |
| Fresh state (no `.venv`) | `.venv` renamed away, then `cmd /c run.bat` | "Found Python 3.12.10 (py -3 …)", "Creating the project's virtual environment (.venv)...", "Installing the app and its dependencies...", pip installed Flask/Flask-WTF/markdown/bleach + transitive deps, app served on 5000 (`/help` → 200), browser opened (`GET /` logged) | **pass** |
| Second run (venv present) | `cmd /c run.bat` again | No create/install messages — straight from the Python line to launch; server already answering when the first poll ran; browser opened | **pass** |
| Port 5000 occupied | Dummy `TcpListener` held 5000, then `cmd /c run.bat` | "Port 5000 is busy, trying the next one...", "Using port 5050 instead of the default 5000.", served on 5050 (`/help` → 200), browser opened on 5050 | **pass** |
| Python missing | Child `powershell.exe` with PATH stripped to System32 (hides `py`, `python`, and the Store-stub alias), `-File run.ps1` | "Could not find Python 3.11 or newer on this machine." with the per-candidate "not found" notes, the python.org/downloads link, the 'Add Python to PATH' tip, exit code 1 | **pass** |
| `run.sh` syntax | `bash -n run.sh` under Git Bash | Clean (exit 0). `shellcheck` not installed on this machine; no real POSIX environment available, so a full run was not exercised | **verified-syntax-only** |

Additional observations:

- The `run.bat` shim's `|| pause` behaves as intended for double-click users: when the app
  process died abnormally (force-killed during testing, the stand-in for a crash), the console
  stayed open on "Press any key to continue . . ." so the failure output remains readable.
  A normal `run.ps1` failure path (e.g. Python missing) exits 1 and triggers the same pause.
- The Store-stub branch (a `python` alias under `WindowsApps` that prints the Microsoft Store
  message instead of running) could not be exercised on this machine because a real Python is
  installed; the detection logic (version probe fails + command resolves under `WindowsApps`)
  is code-reviewed only.
- "All four ports busy" was not exercised end-to-end; it is the same probe loop as the
  port-5050 scenario with an exhausted list, and its message ends with the manual `--port`
  instruction.
- A `.gitattributes` was added alongside the scripts pinning `run.sh` to LF (and the Windows
  scripts to CRLF) so a Windows checkout with `core.autocrlf` can never hand bash a CRLF
  script; `tests/test_launchers.py` guards the working copy the same way.
