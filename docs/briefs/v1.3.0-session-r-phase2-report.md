## Lens 1 — dual-format readiness

### The seam is real and in the right place

Every downstream consumer — render (`viewer/render.py`), FTS (`viewer/search.py`), tagging
(`viewer/tagging.py`, `viewer/state.py`), conversation export (`viewer/export.py`), print
(templates/CSS), inspect (`viewer/inspect.py`), and all read-only routes — consumes the
typed `Export` model and has **zero container knowledge**. The parse→model boundary is
`viewer/parser.py:_parse_zip` (one choke point, shared by the path loader and the in-memory
inspect loader). A new-format loader that normalises into `Export` leaves the entire read
side untouched. The FTS layer extends by adding `kind` values, guarded by an explicit
row-count invariant (`viewer/search.py:185-190`) that forces `_expected_row_count` to be
updated in lockstep — a good tripwire.

### Where the single-zip container leaks (complete inventory)

| # | Leak | Evidence |
|---|------|----------|
| 1 | Required-files check assumes one zip holds `users.json`, `memories.json`, `conversations.json` | `viewer/parser.py:309` |
| 2 | Memories loader hard-requires the legacy list-of-1; the current format is a dict at `memories/<uuid>.json` with `memory_files` | `viewer/parser.py:366` |
| 3 | A directory of zips is interpreted as *multi-batch same-shape archives*, each parsed as a complete export — a directory of category zips would fail per-zip | `viewer/parser.py:271-283`, `_merge_batches` |
| 4 | Batch-index warning keyed to the legacy `-batch-NNNN` filename; current `-000` part naming unrecognised | `viewer/parser.py:28` |
| 5 | Active-export storage is one file, `cache/active_export.zip` | `app.py:58` |
| 6 | Parse-cache key is `(zip_sha256, parser_module_sha256)` — one zip digest | `viewer/cache.py:56-67` |
| 7 | Upload accepts exactly one file field, `.zip` extension required (a manifest `.json` is rejected); parse-before-replace stages one temp file | `viewer/routes.py:762-798` |
| 8 | Inspect accepts one `.zip` the same way | `viewer/routes.py:840-848` |
| 9 | Upload-history schema stores one `zip_sha256` per row; startup dedup compares that single digest | `viewer/history.py:14,142` |
| 10 | Startup-load order and `startup_record` are single-path/single-hash | `app.py:67-100` |
| 11 | `UPLOAD_MAX_BYTES` comment claims "the real export is ~11 MB" — the current reference's conversations zip alone is 38 MB compressed | `viewer/routes.py:748-751` |
| 12 | README and help copy assert the single-ZIP flow (see Lens 6) | README, `viewer/content/help.md` |

**(a) Finding 1 — the app cannot load the format Anthropic now ships.** Leaks 1–2 mean a
current-format export fails at the required-files check regardless of how it is presented.
Everything in the v1.3.0 scope hangs off a new container loader normalising into `Export`
(recommendation: a sibling loader beside `_parse_zip` sharing the per-file parsers, plus
container detection; effort: the core of the version).

**(a) Finding 2 — upload/inspect/fingerprint flows are single-file by construction.** Leaks
5–10 are the storage, cache-key, history, and route surface for the multi-file design the
arc's design record will settle (subset upload, degraded-view banner, manifest role,
fingerprint semantics). Effort: medium; the atomic parse-before-replace pattern generalises
(stage a set, parse the set, swap the set).

**(a) Finding 3 — model slots for current-format render surfaces.** The parser keeps
unknown block *types* (`UnknownBlock`, preserve-and-flag) but silently drops unknown
*fields* on known types — by dataclass construction, `signature`, `summaries`' content,
`thinking_hidden`, `display_content`, `meta.output_format_category`, text-block citation
offsets, and knowledge `links` never reach the model (`viewer/parser.py:544-583`). Whatever
render policy the design record picks needs corresponding slots. (Today a current-format
block would at least surface: the `_message.html` else-branch renders a named placeholder
card for unknown types, e.g. `injected_prompt_block`.)

Positive note: the timestamp helper already tolerates both ISO forms at any depth
(`viewer/parser.py:765-782`), so the current format's Z-form unification costs nothing.

## Lens 2 — 1.4+ readiness

**Portable, mergeable tag state — (c).** The tag store is well-isolated at module level:
pure functions over a passed-in `sqlite3.Connection` (`viewer/tagging.py`), one table
(`conversation_project`: conversation_uuid PK, project_uuid, tagged_at), resolution logic
separate (`viewer/state.py`). `tagged_at` already supports last-write-wins merging. The
obstacle is file-level mixing: `cache/viewer.sqlite` holds the irreplaceable tag table, the
semi-precious `upload_history` log, and the fully derived FTS index (dropped and rebuilt on
every startup, `viewer/search.py:55`). A portable profile wants the irreplaceable state
separable — either a dedicated file or an export/import path for `conversation_project`
(+history). No machine/provenance column exists yet; merging across machines needs one.
Effort for extraction: low-medium; reconciliation semantics remain the hard design part, as
the plan already records.

**Artifact + file-tools extraction — (c).** Touchpoints are ready: `ToolUseBlock.input` is
preserved verbatim (`viewer/parser.py:559-567`), so artifact `create` bodies and file-tool
`file_text`/`str_replace` payloads are already in the model; `docs/artifact-encoding.md`
and `tools/scan_artifacts.py` carry the encoding knowledge. The feature is a render/route
addition, not a parser change. The manufactured-corpus prerequisite in the plan stands.

## Lens 3 — theming readiness (dark mode)

Inventory verdict: **substantially ready — better than expected.**

- `static/style.css` (1,742 lines) already runs on CSS custom properties: 7 tokens defined
  at `:root` (style.css:9-17), **162 `var()` references**, no dangling names. No
  `prefers-color-scheme` handling exists yet, and the only media query is `@media print`.
- **66 hardcoded colour declarations** remain outside the tokens; the dominant leak is
  `white` (33 occurrences — ~20 card/control surfaces wanting a `--surface` token, ~13
  `color: white` on accent fills wanting `--on-accent`). Three semantic banner palettes
  (amber orphan, red load-error, blue inspect; style.css:1364-1419) are fully untokenised
  — nine more tokens. Estimated total: **10–14 new tokens** covers everything.
- **Templates carry zero inline styles; JS sets zero colours** — nothing to migrate.
- **highlight.js**: only the GitHub *light* theme is vendored
  (`static/vendor/highlightjs/github.min.css`, 13 hardcoded colours). Dark mode needs the
  upstream dark theme vendored alongside and scoped — the one change that touches a
  test-pinned contract (`tests/test_highlighting.py:30-34` pins the single CSS link and
  load order; `base.html:9-10` orders theme CSS before `style.css` deliberately).
- **Print CSS is only partially isolated**: the `@media print` block (style.css:1608-1742)
  uses zero `var()` and overrides only four colour surfaces; everything else (code-block
  `--code-bg`, `--muted` text, all `--border` rules) inherits screen tokens, so re-pointing
  tokens for dark mode **would bleed into print**. The cheap, additive fix: a light-value
  token reset inside `@media print` — it cannot regress current print output because the
  block sets no vars today. **(b)** — do this in the dark-mode session.
- No `theme-color`/`color-scheme` metas, no SVGs, no favicon, no colours in Python.

**(b) Finding — dark-mode work list** (for the implementation brief): token sweep
(66 declarations → ~10-14 new tokens), banner triads, dark highlight.js vendoring with the
test-pin update, print token reset, `color-scheme` property + paired `theme-color` metas.

## Lens 4 — test architecture

470 tests, ~20 s, no skips beyond one opportunistic real-data skip, no xfail, no network,
no browser drivers (driven passes live as prose records in session reports, correctly named
as such).

**Coverage map highlights** (full map from the review sweep; layers: unit, client-HTML,
real-rendered-form, asset-text):

- Strong: search (64, unit-heavy with route coverage), conversation export (51 + 17
  real-form parametrised cases), help (26, including a link crawler and verify-negatives),
  No-Project sentinel (24), inspect (16, including byte-identical `cache/` snapshots),
  launchers (20, asset-text by design), memory (16), history (13).
- **Gaps — (c)**: conversations-list `?sort=` options have no test at all
  (`viewer/routes.py:198-200`); project-detail page content (docs, custom instructions,
  project memory as *rendered*) has no coverage — no `test_projects.py` exists, the
  projects pages get only 200-smokes; the home page's six stat counters have no direct
  assertion; the branch switcher's rendered link construction (`sib.branch_args` →
  `?branch=` URLs) is never round-tripped — route tests hand-build the parameters — and
  the `ignored_overrides` banner is asserted only as a return value; `tools/` scripts have
  no tests (local convention, but now three scanners deep).
- **(b)**: `tests/test_highlighting.py:36-47` `ALL_PAGES` omits `/inspect`, which the
  equivalent matrix in `test_help.py` includes — a hole in the asset-include matrix.

**Fixture organisation vs a second format — (a).** All fixtures are legacy-container,
generated deterministically by one registry (`tests/fixtures/build_fixtures.py`,
`FIXTURES` dict, byte-stable `_write_zip`). Adding the current format requires: a
format axis in naming (a `current/` fixture directory is natural since a current-format
fixture is a *set* of files), a builder that can emit multiple outputs per fixture (the
registry assumes one zip per entry), current-format container assembly + the new memories
shape (block-level builders are reusable), and — the expensive part — **conftest
parametrisation**: `tests/conftest.py` is 8 lines with no shared app/client fixture, and
`"synthetic_export.zip"` is spelled 46 times across 21 of 24 test files. Without a shared,
parametrisable export fixture, dual-format coverage means hand-editing every literal.
Recommendation: build the conftest consolidation FIRST in the v1.3.0 test work, then the
current-format fixture set rides it. Effort: medium, mostly mechanical.

**Hygiene — (b), fix while the test area is open anyway:**

- Duplicated setup: the CSRF-token scraper is defined 8 times + 3 inline copies; the
  byte-identical `client` fixture appears in ~12 files; `app_factory` 3 times + 1 inline.
  One conftest each.
- Latent order dependency: `tests/test_export.py:800-802`, `tests/test_inspect.py:66-68`,
  and `tests/test_no_project.py:358-360` rebind `app` module globals (`CACHE_DIR`,
  `ACTIVE_ZIP`, `PARSE_CACHE`) by direct assignment — never undone — while
  `test_history.py:145-148` and `test_startup.py:52-55` do the same job correctly via
  `monkeypatch.setattr`. Passes today; unpinned cross-test coupling.
- Suite runtime is dominated by fresh fixture parse + FTS rebuild inside every
  `create_app` (deliberate: the parse cache is reserved for the active export). Fine at
  20 s; if dual-format parametrisation doubles the matrix, module-scoping the read-only
  client fixtures is the lever. **(c)**.
- **(c)**: no regeneration guard for the checked-in fixture zips — `_write_zip` is
  deterministic, so a rebuild-and-byte-compare test is cheap insurance against drift
  between `build_fixtures.py` and the committed binaries.
- **(d)**: `tests/test_parser.py:154-170` is the suite's only real-data contact — skips
  when `data/data.zip` is absent, asserts aggregates only. Consistent with the privacy
  rules; will need a decision (skip/retire/re-point) when the dev copy becomes a
  current-format set.
