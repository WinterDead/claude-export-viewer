## 1. Scenario 5 — injected-prompt card (reported FAIL)

### Reproduction through the real rendered page

The active set in `cache/active_export/` (the operator's own upload) was used, per the
brief's instruction to reproduce through the real page with its real CSS and JS. The
real export contains nine `injected_prompt_block` blocks, all in one conversation, all
on human turns (feature preambles carrying memory-update instructions). Layer by layer:

| Layer | Finding |
|---|---|
| Template / served HTML | Correct. `<details class="injected-prompt">` with a first-child `<summary>`, no `open` attribute; the full served page is tag-balanced (58 `<details>`, 58 `</details>`, 58 `<summary>`) and the browser's DOM nests every card correctly. Hypothesis (c) disproven. |
| CSS | No forced-open or forced-display rules; the card had its own skin (border, background, summary styling) and the collapse behaviour is the native `<details>` mechanism, which needs no collapsed-state CSS. Hypothesis (b) disproven. |
| JS | Neither `conv_actions.js` nor `print_links.js` touches `<details>` state or intercepts clicks. Hypothesis (a) disproven — there is no page-side collapse wiring to miss; both thinking blocks and the card sit on the same native element. |
| Behaviour, Chromium 148 (app browser pane) | All nine real cards render **collapsed**; clicking the summary toggles open and closed; the body is genuinely hidden while closed (`checkVisibility` false, card height = summary line only). |
| Behaviour, Firefox 155 (this machine's installed Firefox, headless) | The synthetic fixture's card and the real conversation's first card (its message extracted verbatim from the served HTML, loaded with the app's real stylesheet and scripts) both render **collapsed** with the closed disclosure marker. |

**Conclusion: the FAIL does not reproduce on current code in either engine.** No
defective layer exists to name; all three of the brief's hypotheses are disproven by
direct verification. What the operator saw at hand-test time cannot be established
retroactively — a stale cached page or an interrupted render are plausible but
unprovable. The hardening below was applied regardless, per the brief's fix direction.

### Fix applied — one collapsible contract

All six reading-view collapsibles (thinking, injected-prompt, the three
`display-content-json` fallbacks, attachments) now carry a shared `collapsible` class:
`<details class="collapsible …">` with the shared behaviour rule
(`details.collapsible > summary { cursor: pointer; }`) keyed to it, and the per-kind
skins reduced to styling only. One contract, not parallel ones.
`test_reading_view_collapsibles_share_one_contract` pins it: every `<details>` in the
reading view is on-contract, none carries `open`, each opens with its `<summary>`, and
thinking + injected-prompt are both asserted on the contract explicitly. The existing
per-kind tests were updated to the new class strings.

## 2. Hand-test brief corrections

Both corrections are applied to
`docs/briefs/v1.3.0-session-s-operator-hand-test.md` in place, with a dated correction
note in its header.

- **Reset procedure**: step 1.3 replaced with the §C1 text (move `data\` aside, don't

- **History "When" column**: the column renders through `format_local_relative` —
  always relative, coarsening `just now` → minutes → hours → days → months (30 days) →

  "2 days ago"; `test_relative_stays_relative_past_a_day` now pins the threshold
  (25 h → "1 day ago") and the coarser forms (40 d → "1 month ago", 400 d →
  "1 year ago"). §2.6 and §6.5 of the hand-test brief corrected to this behaviour.

Applied verbatim to `docs/format-support-design.md`:

  where both are now cleared citing the report and date. §3's multi-part marker remains
  in both documents, as directed.

Code shipped for the amendments:

- **Mixed containers (A1)**: the parser's two refusal sites now raise
  `MixedContainerError` (subclass of `ExportFormatError`, detailed filenames kept for
  logs); both `/upload` and `/inspect` catch it and render the C11 copy
  (`MIXED_CONTAINER_MESSAGE`) as the error message, previous export untouched.
  Rendered-form tested on both routes (`test_mixed_containers_refused_with_c11_message`,
  asserting the exact copy against the HTML-unescaped response).
- **Multi-part through the UI (A2)**: both routes now collect same-category files and
  group before the last-wins rule — `manifest_part_map` (manifest `filename → part`)
  decides order when it assigns every duplicate a distinct part number; failing that,
  distinct `-NNN` filename suffixes do; otherwise last-wins-with-warning stands
  unchanged. Distinguishable parts flow to the loader **in part order** (the previous
  name-sort before `load_export` is gone), where the existing §3 merge concatenates
  first-wins. Manifest duplicates keep last-wins.
- **Set summary (C3)**: `summarise_set`/`summarise_set_dir` now count per-file and
  render part multiplicity — `5 files: conversations ×2, projects, memories,
  light_metadata` — history rows, inspect banner, and startup footer all inherit it.
- **Tests** (`tests/test_upload_sets.py`, using the `current_two_part/` fixture whose
  part 1 carries a deliberately mutated duplicate of part 0's first conversation):
  suffix-ordered parts supplied out of order (part 0's copy must win); manifest-ordered
  parts with filenames deliberately contradicting the manifest (the manifest must win);
  indistinguishable duplicates still last-wins (pre-existing test, still valid — one
  name carries no suffix); history-row and inspect-banner summaries with ×2; the
  summary unit shapes.

Nuance recorded: a stored two-part set re-parses on a cache-invalidated startup in
directory name order (`_resolve_paths` globs sorted). For suffix-named parts that *is*
part order; a set whose manifest ordering contradicted its filenames would re-merge in
name order at startup. Academic until a real multi-part export is observed — the
provisional §3 status covers it.
